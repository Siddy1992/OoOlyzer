# PRESENT first-round key profiling

This experiment reproduces the row-level profiling workflow used for the masked PRESENT first-round key study without requiring a gem5 source patch.

## Model

For each target nibble `i`, plaintext class `v`, and repetition `r`, the harness creates one secret row and 16 reference rows. The reference rows force the target first-round key nibble to guesses `0..F`. The pseudo-random mask seed depends only on `(i,v,r)`, so the secret row and all 16 references use matched masking randomness.

The four monitored share-pair channels are:

```text
L1  x9  <-> x6
L2  x18 <-> x7
L3  x19 <-> x28
L4  x20 <-> x29
```

For each row, OoOLyzer accumulates the Hamming distance of consecutive writes to a physical register when the previous and current architectural writers form one of these pairs. This compatibility policy is the behavior of the original `leak_tracker.hh` supplied under `experiments/present_key/reference/`.

The profile for a key guess is the mean four-channel leakage vector for each plaintext class. The recovery score is

```text
D_i(g) = sqrt(sum_v sum_j (L_secret[i,v,j] - L_ref[i,g,v,j])^2)
```

where `j` ranges over L1--L4. The minimum-distance guess is selected for each of the 16 nibbles.

## Why no gem5 patch is needed

The original tracker received rename and physical-register write events directly in gem5. The current artifact reconstructs the same state from the standard debug trace:

```text
Rename + Exec + ExecFetchSeq
```

`tool/present_template.py` maintains the current architectural writer for each physical register, the last physical-register writer/value, row state, and L1--L4 accumulators. Row markers are ordinary RV32 register writes generated by the benchmark.

## Workload

The main artifact uses the current RV32 masked PRESENT assembly in `benchmarks/present/RISCV_masked-PRESENT.S`. The key-profiling harness calls the first masked S-box directly after constructing the exact masked state produced by round-0 AddRoundKey. This keeps the experiment focused on the first-round subkey and avoids generating traces for the remaining rounds.

The original C victim, RV64 assembly, tracker header, and recovery script are retained under `experiments/present_key/reference/` for provenance; they are not needed to run the artifact.

With the default `REPS=3`, each target nibble contains:

```text
16 * 3               = 48 secret rows
16 * 16 * 3          = 768 reference rows
                         816 rows total
```

The full experiment runs 272 short gem5 simulations: 17 profiles for each of 16 target nibbles. Keeping each profile in a fresh simulator run makes the secret profile and its matching reference start from the same backend state.

## Bare-metal startup and linker-relaxation safeguard

The generated profiling ELF uses a custom `_start`; there is no C runtime startup and `gp` is intentionally not initialized. GNU RISC-V relaxation must therefore not rewrite address materialization into `gp`-relative accesses. The artifact enforces this in two places:

```text
generated harness:  .option norelax
linker:             -Wl,--no-relax
```

`build_present_template_case.sh` also runs `riscv64-unknown-elf-objdump -d --disassemble=_start` after linking and rejects the ELF if `gp` appears in `_start`. Correct address loads should remain PC-relative (`auipc` plus an immediate/add instruction), rather than `addi ...,gp,...`. This fixes the earlier failure mode that could surface in gem5 as a page-table fault at a small negative virtual address such as `0xfffffffffffff814`.

For a manual one-case verification:

```bash
REPS=1 ./scripts/build_present_template_case.sh 0 secret
riscv64-unknown-elf-objdump -d --disassemble=_start \
  build/present_key/nib00/secret/present_key.elf
```

No `gp` operand should appear in the `_start` disassembly.

## Commands

Run the input-matching check:

```bash
python3 scripts/test_present_template.py
```

Run one secret profile and one reference profile:

```bash
REPS=3 ./scripts/run_present_template_case.sh 0 secret
REPS=3 ./scripts/run_present_template_case.sh 0 reference 1
```

Run the complete key experiment:

```bash
./scripts/run_present_key.sh
```

The expected result is:

```text
Recovered first-round key: 123456789ABCDEF0
Expected  first-round key: 123456789ABCDEF0
Correct nibbles: 16/16
present-key: match
```

For a shorter diagnostic run:

```bash
NIBBLES="0 1" REPS=1 ./scripts/run_present_key.sh
```

A partial run does not perform final key ranking.

## Outputs

Each nibble writes a `secret/` directory and `g00/` through `g0f/` reference directories under `results/present_key/nibXX/`. Each profile contains `template_meta.csv`, `gem5_physreg_leak.csv`, `gem5_physreg_events.csv`, and `analysis.json`.

The full run additionally writes:

```text
results/present_key/merged/template_meta.csv
results/present_key/merged/gem5_physreg_leak.csv
results/present_key/merged/gem5_physreg_events.csv
results/present_key/recovery.json
```

Raw traces are stored under `m5out/present_key/nibXX/` only while a case is being analyzed. They are deleted by default. Use:

```bash
KEEP_PRESENT_KEY_TRACES=1 ./scripts/run_present_template_case.sh 0 secret
```

when trace inspection is required.

## Cleaning only the key experiment

```bash
./scripts/clean_present_key.sh
```

This removes only key-profiling build products, traces, and results. It does not remove the structural PRESENT, Toffoli, or PINI outputs.
